# Melty runs your own Claude Code for you

"Melty" is Melty Labs, and its current product is **Conductor**. The old Melty site, melty.sh, now redirects to conductor.build. Conductor never gets its own access to Claude. It starts the **real, unmodified Claude Code program** and lets that program use whatever account it is already signed in with: your own Pro/Max plan (through `claude /login`) or your own API key ([Conductor docs](https://www.conductor.build/docs/reference/harnesses/claude-code)). Anthropic's terms as of November 2026 allow exactly this. A person may sign in to the unmodified Claude Code program with their own subscription, even inside someone else's product. An app may not offer its own "Sign in with Claude" button, and it may not collect, store or pass along people's Claude login tokens ([Anthropic legal and compliance](https://code.claude.com/docs/en/legal-and-compliance)). So the earlier advice was mostly right for the way claude-room works today. A server that calls Claude for people cannot use their subscriptions. But that advice left out one legal door, and it is the one Melty uses: run Claude Code on each person's own computer and let your app only carry the chat. Below is a design for claude-room that uses that door. Each person can choose their own subscription or their own API key, and your server never touches anyone's Claude login.

## The right "Melty" is Melty Labs, now called Conductor

Two products use the name. The one you mean is **Melty Labs** (Y Combinator, summer 2024, founders Charlie Holtz and Jackson de Campos). In 2024 it released an open-source AI code editor called Melty ([YC launch](https://www.ycombinator.com/launches/Llk-melty-open-source-ai-code-editor-for-10x-engineers)). That editor has effectively been replaced. The company now builds **Conductor**, a Mac app that runs several Claude Code agents side by side ([conductor.build](https://conductor.build/); [YC company page](https://www.ycombinator.com/companies/conductor)). The shared-chat part arrived on **July 30, 2026** with **Conductor Cloud**. You can share a workspace link with teammates, see who is active, and "prompt agents together in real time" ([Conductor changelog 0.78.0](https://www.conductor.build/changelog/0.78.0-introducing-conductor-cloud)). Inside a Cloud organization, everyone sees the transcript update live, along with avatars and typing indicators ([Conductor collaboration docs](https://www.conductor.build/docs/cloud/collaboration)).

The other Melty, at melty.world, is unrelated. It is a Windows app from Stella Montis Inc., launched in October 2026, that mixes PC games into mashups. It mentions Claude Code only as a tool modders can use ([tau-home](https://tau-home.com/en/post/melty-one-click-pc-game-mashup-platform-launch/)).

One caution: some older write-ups describe Conductor as single-user only. That was true before Cloud launched. It is no longer true.

## Conductor uses your Claude Code login and never sells you Claude

The key fact is simple. **Conductor does not talk to Claude itself.** It runs Claude Code, either a copy it bundles or the one you installed yourself, and Claude Code handles the login. Conductor's FAQ says: if you are logged into Claude Code with an API key, Conductor uses that, and "if you're logged in with Claude Pro or Max, Conductor uses that" ([Conductor FAQ](https://www.conductor.build/docs/faq)). The company also states that it "does not bill or resell model usage". The usage is charged to whichever subscription or key Claude Code is using ([Conductor providers guide](https://www.conductor.build/docs/guides/providers)). The same guide gives a practical warning that matters for your app too. If the `ANTHROPIC_API_KEY` environment variable is set, Claude Code may quietly switch to API billing instead of using the subscription.

The cloud version works a little differently, and this is where it gets less clear. In Conductor Cloud, each member adds "a personal subscription token or API key". The changelog points users to the `claude setup-token` command, which creates a one-year login token for a Claude plan ([Conductor Cloud getting started](https://www.conductor.build/docs/cloud/getting-started); [Claude Code authentication](https://code.claude.com/docs/en/authentication)). Organization admins can also add a shared API key, and that key **takes precedence** over members' personal keys. The docs do not say whose credential runs when teammate B types into teammate A's shared workspace. Conductor's paid plans (Pro, Team) charge for the app, collaboration and cloud computers, not for Claude tokens ([Conductor Cloud FAQ](https://www.conductor.build/docs/cloud/faq)).

| Conductor mode | Who signs in to Claude | Where Claude runs | Who pays for Claude |
|---|---|---|---|
| Local Mac app | You, through Claude Code's own `/login` | Your Mac | Your Pro/Max plan or your API key |
| Cloud workspace | Each member pastes a subscription token or API key into Conductor | Conductor's cloud sandbox | That member, or the org's shared API key |

## Anthropic's November 2026 rules: the local way is allowed, stored tokens are risky

Anthropic's current Claude Code legal page has two parts that matter here. The first is a ban. Third-party developers may not "offer Claude.ai login into their own applications, or … route requests through Free, Pro, Max, or Ultra plan credentials on behalf of their users". They also "may not collect, store, or intermediate Claude.ai credentials or session tokens". Sign-in must happen through Anthropic's own flow. The second is an exception. The rules do not stop "an end user from signing in to **the unmodified Claude Code binary** with their own Claude subscription, including where a platform hosts Claude Code" ([Anthropic legal and compliance](https://code.claude.com/docs/en/legal-and-compliance)). A product that ships or hosts Claude Code must also follow these rules: it accepts Anthropic's Commercial Terms, it does not change the binary or remove its login options, and it does not "pay for, resell, or intermediate Claude usage" for its users. Each user pays under their own agreement with Anthropic.

Measured against those rules, **local Conductor fits cleanly**. It runs your unmodified Claude Code on your own Mac with your own login. **Conductor Cloud is the grey part.** Storing members' `setup-token` credentials on Conductor's servers sits uneasily with "may not collect, store … session tokens". It could be acceptable if Anthropic treats that token flow as its own sign-in, or if the two companies have a private agreement. Nothing public settles it either way. We found no Conductor statement about Anthropic approval, and no report that Anthropic has acted against Conductor.

These rules have changed a lot this year, so treat them as moving. In **January 2026** Anthropic began blocking third-party tools that pretended to be Claude Code to use Pro/Max logins. In **February** it wrote into its docs that using subscription tokens in any other product broke the Consumer Terms, and OpenCode removed Claude subscription support after "anthropic legal requests" ([The Register](https://www.theregister.com/2026/02/20/anthropic_clarifies_ban_third_party_claude_access)). In **April** Boris Cherny, who leads Claude Code, said subscriptions would no longer cover third-party tools like OpenClaw. Those tools would have to use paid "extra usage" or an API key instead ([Boris Cherny on X](https://x.com/bcherny/status/2040206440556826908)). In **June** Anthropic paused a planned change to SDK billing, and its help center now says Agent SDK, `claude -p` and "third-party app usage still draw from your subscription limits" ([Claude Help Center](https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan)). Two things remain unchanged. Anthropic can enforce its rules "without prior notice", and plan limits assume "ordinary, individual usage" ([Anthropic legal and compliance](https://code.claude.com/docs/en/legal-and-compliance)). Sharing one subscription between several people is forbidden outright: you "may not make your Account available to anyone else" ([Consumer Terms](https://www.anthropic.com/legal/consumer-terms)).

The developer side is still a little unsettled. The Agent SDK page says that, unless Anthropic has approved it, third-party developers may not "offer claude.ai login or rate limits for their products" ([Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview)). OpenCode re-added subscription support on October 30, 2026 by running the real `claude` program through the Agent SDK. Anthropic has not publicly responded ([CellCog](https://cellcog.ai/blog/opencode-claude-subscription/)). Mastra has proposed the same move and is asking Anthropic to confirm it ([Mastra issue #29198](https://github.com/mastra-ai/mastra/issues/29198)). In short, **nobody has an official "yes" for a third-party app that runs on users' subscriptions**. The local, unmodified-Claude-Code pattern is the one the current text most clearly allows.

## A compliant claude-room: one shared room, one local Claude per person

The earlier answer said a custom app "can't use subscriptions". That is true for today's claude-room. Its server takes each person's key and calls the Anthropic API itself, so a subscription cannot fit into that design. The fix is to **move the Claude call out of your server and onto each person's own computer**. Some small multiplayer tools already work this way. Claude Squad's multiplayer mode has each teammate connect "their local Claude Code" with one command, and keys "never leave each user's machine" ([Product Hunt: Claude Squad](https://www.producthunt.com/products/claude-squad/reviews)). team-coding gives each participant a private Claude that runs on their own machine ([GitHub: team-coding](https://github.com/m3nadav/team-coding)).

The design has three parts. First, the **room server** you already have (Node plus `ws`) keeps doing what it does well: rooms, invite links, live messages, history in `data/`. It just stops calling Claude for subscription users. Second, each person who wants to use their subscription installs a small **companion** program (for example `npx claude-room-companion`). Third, Claude Code runs on that person's computer and is signed in by the person themselves.

```
 Browser (Ana)  ─┐                        ┌─ Browser (Ben)
                 ├──► Room server (relay) ◄┤
 Companion (Ana) ┘   messages only,        └─ Companion (Ben)
   │                 never Claude logins       │
   ▼                                           ▼
 Claude Code on Ana's PC                     Claude Code on Ben's PC
 (signed in with Ana's Pro plan)             (signed in with Ben's Max plan)
```

Here is what happens when Ana presses **Ask Claude**. The server sends the request **only to Ana's own companion**. The companion turns the room history into a prompt, with each line marked with who said it, just as `server.js` does now. It then runs the official Claude Code. That can be the Agent SDK, which runs the Claude Code binary, or `claude -p`. Claude Code uses whatever login Ana gave it when she ran `claude /login` herself. The answer streams back through the companion to the room and is labelled something like "Claude · via Ana's plan". The usage counts against Ana's subscription, because Ana asked.

Most of the compliance work is in a few strict rules for the companion. It must **never read, copy or upload** anything from `~/.claude` or the macOS Keychain. It must never ask for a `setup-token`, and the room server must never store one. It must **remove `ANTHROPIC_API_KEY`** from the child process's environment, so Claude Code does not silently switch to API billing. It must use Claude Code exactly as published. Limit what it can do through Claude Code's own settings, for example no file or shell tools for a plain chat room, rather than patching the program. Even that kind of configuration has not been tested against the "must not be modified" rule. Finally, **only the owner's own click** may start their companion. Other people's messages are background for the prompt, never commands that run on Ana's computer. That keeps each subscription for "ordinary, individual usage". It also stops a stranger in the room from running tools on someone else's machine.

Keep the current API-key path as a second option. In Settings, each person picks "my own API key", which runs through the server as it does now, or "my Claude subscription (companion)". People who do not want to install anything can still take part. For a public version, three more steps reduce the risk. Accept Anthropic's Commercial Terms. Do not use "Claude Code" in your product's name or logo; saying in plain text that it "runs Claude Code" is allowed ([Anthropic legal and compliance](https://code.claude.com/docs/en/legal-and-compliance)). Ask Anthropic sales to confirm your setup, as that page suggests.

Two things to avoid, even though some products do them. Do not build a cloud version where people paste a `setup-token` into your server, which is what Conductor Cloud does. Do not let one person's plan answer everyone in the room, which is how tools like Jam work ([Product Hunt: Jam](https://www.producthunt.com/p/jam-7/jam-0825b8cb-4607-45c1-b1bb-fdedf369a09d)). The first collides with the token rule. The second is account sharing.

## Conclusion

The trick behind "Melty" is not a special deal with Anthropic. It is a choice about where Claude runs. When the Claude call happens inside the user's own, unmodified Claude Code, the subscription stays the user's own, and the app is just a nicer window and a shared room. That one change makes "everyone uses their own subscription" possible for claude-room as well. The cost is that every subscription user must install a small companion and keep their computer on while they chat.

The policy ground is still moving. Anthropic tightened its rules three times in the first half of 2026 and loosened billing once. It has not commented on the newest SDK-based tools, and it can enforce without warning. Build the companion so it can be switched off cleanly. Keep API keys as the fallback that always works. Treat the subscription mode as allowed today under the "unmodified Claude Code" exception, but not guaranteed tomorrow.
